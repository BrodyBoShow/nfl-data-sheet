**Rendering facts verified for Next 16 (context7, `/vercel/next.js/v16.2.9`):**
- Leave `cacheComponents` off, which is the default. With it on, `export const
  revalidate` is a build error, and `generateStaticParams` can't return `[]`.
- `export const revalidate = 600` is route-segment time-based ISR: serve stale, then
  regenerate in the background.
- **Dynamic routes (`/[season]/[week]`, `/game/[gameId]`) must export
  `generateStaticParams` returning `[]`.** Otherwise paths aren't ISR-cached at runtime.
  Quoting the docs: "To enable revalidation (ISR) for paths at runtime, you must return
  an empty array from `generateStaticParams` or use `export const dynamic =
  'force-static'`."
- `dynamicParams` stays at its default `true`, so every path renders on first request.

**Key type:** `.env`'s `SUPABASE_ANON_KEY` is the **legacy anon JWT**, not a
`sb_publishable_…` key.
- Whether the project also offers a publishable key is only visible in the dashboard
  (Settings → API Keys). None of the available MCP tools reads keys.
- Rotating a legacy key means rotating the JWT secret, which also rotates the
  service-role key. The pipeline uses neither, so rotation is still harmless here.

**Hosting:** the repo `BrodyBoShow/nfl-data-sheet` is owned by a GitHub **User**

## 2. Read contract and anon-key scope

### 2a. Access model: migration `0026_web_read_access.sql` (step 0)

- **Grants and RLS are the boundary. Views are convenience.** Row scope lives in RLS
  policies and column scope in column grants. So even if `public` were re-exposed
  through the API, anon would still see only what's listed here.
- **Close everything first:**
  - `REVOKE ALL` on every table, sequence, and function in `public` from `anon` and
    `authenticated`.
    - Before 0026, anon held full grants on **every** public table. RLS default-deny
      (0007) was the only thing blocking it.
  - `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE ALL ... FROM
    anon, authenticated`.
    - Live `pg_default_acl` showed `postgres` auto-granting anon full rights on every
      new public table, sequence, and function.
- **Found while planning, fixed in 0026:** `injuries_backup_pre_changelog` (25,653 rows,
  including raw ESPN/Sleeper payloads) had **RLS disabled** and full anon grants.
  - It was readable and writable by anyone holding the anon key. The key hadn't shipped
    anywhere, so the exposure was latent.
  - Drop it after Sunday 2026-09-27's slate runs clean through the changelog path
    (§8 Q3).
- **Then open exactly three tables, read-only:**

| Table | Column grant to `anon` | RLS policy (`FOR SELECT TO anon`) |
|---|---|---|
| `games` | `game_id, season, week, home_team, away_team, gameday, gametime, location`. Exactly the L3 identity set, so scores and lines are unreadable at the grant level. | `USING (true)` |
| `matchup_cards` | every column except `content_hash`, `updated_at` | `USING (true)` |
| `signals` | every column except `id` | `USING (player_id IS NULL)`, so v1 exposes no player rows (§8 Q2) |

- **Schema `web`:** `security_invoker = true` views over those grants (they pass
  Supabase's security linter, which flags definer views). `GRANT USAGE ON SCHEMA web`
  and `SELECT` on the views to anon.
- **Dashboard step (user, after 0026 is applied):** Data API → Exposed schemas = **`web`
  only**.
- **No write path exists for anon:** no INSERT/UPDATE/DELETE grant and no write policy
  on any object.
- **Two things 0026 doesn't touch:**
  - `supabase_admin` has the same permissive default ACL in `public`. `postgres` can't
    alter it. It only applies to objects `supabase_admin` itself creates, and every
    table here is owned by `postgres`.
  - `pg_graphql` isn't installed, so there's no GraphQL surface.

### 2d. What an attacker holding the key can pull

**Treat the key as public**, even though v1 keeps it **server-only** (env var without
`NEXT_PUBLIC_`, so it never reaches the browser bundle; step 9 greps the build output).
With the key and the project URL, an attacker can:

- **Read** all 2,499 schedule rows, 8 identity columns each.
- **Read** every matchup card, including frozen ones (~270/season). That's exactly what
  the site renders.
- **Read** every team- and game-scope signal row since 2019 (~163k rows, ~40 MB as
  JSON). Also exactly what the site renders, in bulk. PostgREST caps each request at
  1,000 rows, so a full dump is ~165 requests.
- **Nothing else:**
  - no player rows;
  - no scores or lines;
  - no staged tables, no raw per-book odds, no injury text;
  - no `agent_runs` errors/meta, no `projection_log`/grades, no `players`/crosswalk;
  - no writes;
  - no RPC.

**Worst realistic abuse:** repeated bulk dumps to burn the 5 GB egress. At ~40 MB per
dump that takes ~125 full dumps in a month, and it restricts the shared project (§1).
**Response:** rotate the key. Prefer the new `sb_publishable_…` key if the project has
one, since it rotates without touching anything else; the pipeline uses
`SUPABASE_DB_URL`, not an API key.

`scripts/verify_anon_access.py` (step 0) asserts all of the above live, so this section is
tested rather than just claimed.

- Signal display names come from `web/lib/signal-labels.ts`, and an unknown signal name

- A P7 player row slots under its unit (e.g. "ATL pass offense → WR rows") in the same

## 4. Visual spec

Decided once here, implemented once in `web/app/tokens.css`. The target is a statistical
almanac or terminal: data starts within the first ~100px of every page.

**Type.** IBM Plex Sans for UI and prose; IBM Plex Mono for every number, team code, and
signal name. Weights 400/500/600 only.

| Token | px / line-height | Use |
|---|---|---|
| `--t-cap` | 11/14, 500, uppercase, +0.06em | column heads, section labels, tags, footnotes |
| `--t-small` | 12/16 | secondary cells, raw signal names, `as_of` stamps |
| `--t-base` | 13/18 | table cells, default UI |
| `--t-prose` | 15/22 | `/method`, `/sources` body only |
| `--t-head` | 16/20, 600 | section heads |
| `--t-title` | 20/24, 600 | one per page (e.g. `ATL @ GB`) |

No other sizes.

**Numerals and values:**
- Tabular, lining figures, right-aligned, with a fixed number of decimals per signal
  type (EPA 3, rates as % with 1, points 1, lines 1).
- Minus is U+2212.
- Spreads are team-labeled (`GB −4.2`, `PK`), never the raw home-negative number.
- Null is `—` in `--ink-3`, with a `title` giving the reason where known (e.g. "no row:
  fewer than 2 books"). Null is never shown as 0.

**Palette.** No green/red, no team colors, no indigo/purple, no gradients.

| Token | Light | Dark | Use |
|---|---|---|---|
| `--bg` | `#F7F6F2` | `#101112` | page |

| `--ink` | `#16181A` | `#E4E2DC` | data |
| `--ink-2` | `#5B5F63` | `#9A9EA2` | labels, secondary |

| `--warn` | `#8A5300` | `#D9A13B` | **pipeline state only:** stale, missing, not validated, not projected |

Dark mode follows `prefers-color-scheme`.

**Density and layout:**
- Max width 1120px, left-aligned, 16px gutters.
- No hero, no marketing copy, no cards-as-boxes, no shadows. Border radius 0 (2px max on
  tags).
- Sections are separated by a 1px rule plus a `--t-cap` label.
- The game view uses 2 columns at ≥960px (left: lines and the model's arithmetic; right:
  context), 1 column below that.
- Wide tables scroll inside their own container with a sticky first column. The page
  itself never scrolls sideways.
- No icons, emoji, logos, or images.

**Table treatment:**
- Row height 24px, cell padding 2px 8px.
- Head row in `--t-cap` `--ink-2` with a bottom rule. No zebra striping.
- Day groups (THU / SUN / MON) are full-width `--bg-alt` rows.
- Units go in headers, not cells.
- In signal tables, value · n · stab are always adjacent columns. A signal cell shows its
  display name, with the raw `signal` name beneath in `--t-small` mono `--ink-3`.
- **A league-percentile column (`Pct`) appears right after the value only when some row
  in that table has a `league_pct`** (amended 2026-09-25, was: a reserved `Rank` column
  rendering `—`). Today every `league_pct` is null, so the column is absent. When
  Efficiency fills it (P2 pending amendment), the column appears with no code change:
  still a data change, not a layout change (§8 Q5). It's labeled `Pct`, not `Rank`,
  because the stored value is a 0–100 percentile, not a rank.
- **Low-stability values are dimmed** (added 2026-09-25). A value whose `stability` is
  below the **stability floor** renders in `--ink-3`, with a title giving its stability
  and its league-average share. Its n and Stab stay at full weight, since they explain the
  dimming. One legend line under the table defines the grey, only when something is grey.
  - The floor is the lowest model-input stability of any backtested game: the bottom of
    the lowest bucket's `stability_range` in `model_coefficients.json`, now **0.2262**
    (`epa_per_play_def` in a week 1: last season's prior alone, `r_def` × 1). It's read at
    build time into `backtest-summary.json`, so a refit moves it.
  - Why that floor: `stability` is the share of a value that isn't the league average
    (`docs/signals.md`). Below the floor, a number carries less team information than
    anything the backtested model has ever used as an input.
  - Applied to the efficiency pairings and the no-card team table. Not applied to the
    model's arithmetic, since those are the model's own inputs and sit at or above the
    floor by construction.

Kickoff (ET) · Matchup (`ATL @ GB`, neutral marked `vs`) · Market spread (latest) · Model
spread · Market total · Model total · Stab (`LOW`/`MID`/`HIGH` as text) · Status
(`LOCKED 15:28` / `PROVISIONAL · locks 18:15` / the status label when not projected) ·
Venue (roof code, temp/wind only when `weather_status = 1`).

**No edge column** (§5, §8 Q1). Default sort is kickoff, and no column is sortable in v1.

## 5. The honesty requirement, concretely

The approach: **attach the evidence to the number, instead of stacking disclaimers above
it.** A reader who knows football reads a correlation of −0.03 faster than a paragraph.
There are three devices, each used once, plus vocabulary rules.

1. **A status line in the header of every page.** One line, `--t-small` mono, parsed
   from the backtest report at build time:
   `Backtest 2020–25, 1,615 games out of sample: margin MAE model 10.32 · closing line 9.76 ·
   edge vs result r −0.03 [−0.08, 0.02] · not validated`
   - **Wording as built (step 4), changed from this plan's draft.**
     - The draft ("model − market vs result … · edge not validated → method") ran ~152
       monospace characters, one more than the 1,088px content width holds at 12px. So
       it wrapped at 1280px.
     - "edge vs result" replaces "model − market vs result". Its tooltip gives the full
       definition and the report's 3-decimal figures.
     - "not validated" itself links to `/method#edge`, replacing a separate "→ method".
       The claim now links to its evidence.
     - On phones it wraps only at the `·` separators.
     - The validation phrase is derived from the data. It reads "validated: <buckets>"
       if any bucket ever validates.
   - It isn't dismissable and isn't a banner. It sits in the header rule, like a
     terminal status bar.
   - The backtest is one click from every page (`/method`), and the result is readable
     without that click.
2. **An inline tag on every edge value.** The edge only appears on the game view, as a
   row labeled `Model − market`. The tag is part of the value, not a footnote:
   `0.3 toward ATL  [NOT VALIDATED]`
   - The tag has a `--warn` hairline border and links to `/method#edge`.
   - Its `title` holds the card's bucket evidence, e.g. "Backtest 2020–25, low input
     stability (n 535): r −0.024 [−0.108, 0.056]."
   - `validated` comes from `card.uncertainty.edge_validated`; the r/CI/n come from
     `model_coefficients.json` → `calibration.buckets[bucket].edge_validation`. They're
     shown only when the card's `projection.model_version` equals the file's; otherwise
     the tag shows the flag alone.
   - If a future model is ever validated, the tag reads `[VALIDATED]` with the same
     treatment: no color, no emphasis.
3. **The stability bucket sits next to every projection.** That's a `Stab` column in the
   week view, and a row directly under the model line in the game view:
   `Input stability  LOW (0.49)`
   - Its `title`: "Share of each rating that comes from this season's plays and a
     trusted prior, rather than the league average. Not confidence in the result."
   - Right below it, once per game: `Typical miss, any projection (model or market)  ≈13
     pts`, from `uncertainty.outcome_noise`. This puts the model and the market on equal
     footing instead of implying a precise model.

**What the app never does:**
- **No pick vocabulary** in UI strings: pick, play (as a bet), bet, best, lean, value,
  fade, hammer, sharp, lock (as a bet), confidence, recommend.
  - "Lock" appears only as the pipeline term `LOCKED`, with its time.
  - The card's `edge.vs_current.summary` ("model favors ATL by…") is **not rendered**;
    the app shows neutral `toward ATL` instead.
- **No emphasis on edges:** no ranking, sorting, filtering, or highlighting by edge. No
  "biggest edges" list. Edge digits use the same `--ink`, weight, and size as every
  other number: no bold, arrows, or check marks.
- **No edge in the week view.** Market and model lines sit side by side, so the gap is
  visible, but there's no scannable edge column. A scannable edge column trains exactly
  the behavior the backtest says is unjustified (§8 Q1).
- **A favorite flip is marked as a boolean, never as a size** (user decision 2026-09-24,
  option A).
  - When the model and the market favor different teams, the model cell reads `flipped
    CHI −5.4`. The word is in secondary ink, before the value so the numbers stay
    aligned, and the tooltip reads "The model and the market favor different teams. How
    far apart they are isn't marked."
  - A 0.2-point flip and a 10-point flip look identical. A pick'em on either side is not
    a flip.
  - The favored team comes from one function (`favoredTeam`), shared with the spread
    label, so the label and the marker can't disagree.
  - Options B/C were rejected. They express the model line against the market favorite,
    which makes the disagreement the difference of two adjacent signed numbers,
    computable at a glance: an edge column arriving as a layout improvement.
- **No record, win rate, or ROI anywhere in v1.** Grades aren't exposed (§8 Q7).
- **No projection shown when `projection_status ≠ 1`**, only the status label in
  `--warn`.
- **Before the lock**, the projection is marked `PROVISIONAL · locks from 07:00 ET`, so
  a moving number isn't read as the claim.
- **After the lock**, the lines block shows three columns: `Market at lock` · `Latest
  pre-kickoff market` · `Model (locked)`.
  - Nothing is computed; the values come from `edge.at_lock` and `edge.vs_current`.
  - This keeps the week-3 stale-line problem visible (ATL@GB: −6.5 at lock vs −4.5
    latest) instead of hiding it.
- **"In the model" and "context" are always separate sections:**
  - The model section is the arithmetic from `projection.decomposition`:
    `α + HFA + β_off × centered + β_def × centered = points`, per side, every value read
    from the card.
  - Everything else sits under `Context: not used by the model` (the card's own
    `in_model: false`).
- **Precision is capped at 1 decimal** for projections and edges.

**Enforced by test (step 8):**
- A vitest suite renders the fixture pages and fails on the banned vocabulary.
- It fails on any edge value without a sibling tag.
- It fails on any projection without a stability bucket in the same row/section.

## 6. Game view layout (single card, top to bottom)

1. **Title row:** `ATL @ GB`, then `2026 · WK 3 · THU 09-24 20:15 ET · home` (or
   `neutral`), then the status (`LOCKED 15:28 ET, 4.8 h pre-kickoff` / `PROVISIONAL` /
   the status label), then `card as of …` (`matchup_cards.as_of`, which is when the
   content last changed).
2. **Lines** (left): spread and total rows × market columns and the model column, plus
   the `Model − market` row with its tag, the stability row, and the typical-miss row.
3. **Model arithmetic** (left): the two-side decomposition table. For each term: value
   · week mean · centered · β · contribution · n · stab. `model p5-v1`.
4. **Context: not used by the model** (right):
   - Efficiency pairings, two tables (`GB offense vs ATL defense`, reverse), 19 rows
     each: display name / raw name · off value · (pct) · n · stab · def value · (pct) · n
     · stab.
   - Market detail: open/latest/move/per-day, book range, book counts, set changed,
     crossings, straddle with its card note, open basis, capture lead hours.
     `implied_team_total` and `win_prob_novig` go under a "market-implied" label.
   - Environment: weather status, roof, surface, and the weather values labeled
     `Outside wind (10 m est.)` with the **"Weather data by Open-Meteo.com" credit on
     the block itself**. Rest, travel, and tz per team, with an OSM credit link to
     `/sources`.
   - Availability: OL and secondary flagged counts per team.
5. **Raw signal rows** (`<details>`, collapsed): the Q6 rows as a flat table with
   `as_of`. Headed: "Current table values. The card above is frozen at its last change
   and may differ."
