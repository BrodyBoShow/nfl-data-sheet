## Scope
- **Usage and role analyst** (`usage.py`): snap share (offense, defense, ST, for every
  player who takes a snap), target share, air-yards share, red-zone/goal-line/end-zone
  share, carry share, week-over-week deltas. Reads `player_week`/`snaps`. Writes
  `player_usage_week`.
- **Player efficiency analyst** (`player_efficiency.py`): per-player rate stats for
  receiving, rushing, passing, and defense. It's the individual-side counterpart to P2's
  team-level Efficiency analyst. Reads `player_week`, `ngs`, `pfr_advstats`, `snaps`,
  and the new `player_game_pbp` and `participation_player_season` staged tables. Writes
  `player_eff_week`.
- **Scheme analyst** (`scheme.py`), team-level, writes `signals`:
  - pass rate over expected, neutral pace
  - play-action/motion/RPO/screen rates, box counts, blitz/pressure rate
  - approximate personnel (labeled as approximate)
  - run defense by gap/direction, PFR nearest-defender coverage-proxy splits
  - participation-derived man/zone and coverage-shell tendencies, labeled as
    multi-season history (see "Participation labeling rule")
- **nflverse bulk collector, extended** (not a new collector: participation is the same
  nflverse-data release family, one collector per source family):
  - Widened `ngs`/`pfr_advstats`/`ftn` columns.
  - A player-keyed pbp+FTN count aggregation (`player_game_pbp`).
  - A participation player-season aggregation (`participation_player_season`, tag
    `pbp_participation`), gated by that tag's own `timestamp.json`.
- **Retention job** (L0, `pipeline/orchestration/retention.py`): the decided policies
  L2 and L4 below.
- **Intel collector**: ESPN NFL news feed, official team RSS where available, Sleeper
  trending players as a news-spike indicator. Dedupe by URL + text hash. Rule-based
  tagging only (keywords + crosswalk name matching): team, player_id, category (injury,
  depth chart, suspension, coaching, signing/release/trade). No LLM calls.

## Decisions (user, 2026-09-25)
1. **Shape:** wide per-analyst player tables. **Team-level signals stay in `signals`.**
   The single-shape contract still holds for everything the model reads; the exception
   is player detail only (CLAUDE.md layer rules, `docs/signals.md` "Player tables").
2. **Detail:** the full version. Every metric stores season-to-date (STD, prior-blended),
   this game, and last-4 games. The last-4 values answer "is this player trending."
3. **Retention:**
   - **L2 yes:** staged nflverse player tables keep only `[season-1, season]`.
   - **L4 yes:** after a season ends, its weekly player-table rows collapse to each
     player's final row.
   - **L5 deferred:** the `signals.inputs_version` lookup table.
   - **L3 not decided:** trimming `injuries.raw`. First find out whether the changelog's
     ~450 rows/day are real changes or hash churn (open item 1).

   It's the plan for before the 2028 offseason; revisit then.

   attribution, the same as FTN.

6. **A `--seasons` run of `player_week`/`snaps` without `--force` stops the live refresh
   (filed 2026-09-30, not fixed).** It's the same class as step 4's scoped-run finding
   (`--datasets team_week` advancing `nflverse:pbp`, so `player_game_pbp` would never see
   those games).
   - Both tables are gated on a season-blind per-tag key, `nflverse:stats_player` and
     `nflverse:snap_counts` (`nflverse_bulk.py`, `_is_stale`). The key holds the tag's
     timestamp, never the seasons it was stored for.
   - So `nflverse_bulk --datasets player_week,snaps --seasons 2018-2018` does one of two
     things without `--force`:
     - The tag hasn't moved: it prints `skipped_fresh` and loads nothing.
     - The tag has moved: it loads only 2018, then advances the key to live in `store`.
       The next scheduled run sees the tag fresh and skips 2025–2026. That season's
       corrections stop arriving, and nothing reports it.
   - **`--force` was required for the step 7 backfill (2026-09-30), and was used.** A
     forced run skips `should_run` and records no key (`store` skips a dataset whose tags
     have no live timestamp). Both keys were unchanged after runs 836 and 849.
   - Fix, when it's done: built-from or season-aware keys, matching what
     `player_game_pbp`/`participation_player_season` already have (`_BUILT_FROM_GATED`,
     step 4). `team_week`, `ftn`, `ngs` and `pfr_advstats` have the same exposure to a
     `--seasons` run. `depth` doesn't, because it fetches `ctx.season` only.

### Coverage: who covered whom
**No free source says which defender covered which receiver on a snap.** That takes
tracking-derived matchup charting (PFF, SIS, NGS's non-public matchup product). The
closest proxies, and how each differs:
1. **PFR `def_targets`/allowed stats** (best in-season proxy): per defender per game,
   attributed by PFR's charting to the defender judged responsible on *targeted* plays.
   - No untargeted coverage snaps, so no real denominator.
   - No receiver identity: these are game aggregates.
   - Charting judgment, not tracking.
2. **pbp defender credits** (`pass_defense_*`, tackler, INT): play-level, and on the
   same row as `receiver_player_id`, so it is a real receiver↔defender link. But it only
   exists when that defender broke up, intercepted, or tackled, and a tackle isn't
   coverage. It's biased toward completions and PDs.
3. **Participation** (historical only): on the field isn't covering. It supports
   receiver-vs-man/zone/shell splits, and an on-field-dropbacks denominator for PFR
   targets, as priors only.
4. **NGS `avg_cushion`/`avg_separation`**: distance to the *nearest* defender, identity
   unknown, thresholded.

Any signal built on these is documented as what it is, never as a matchup or a
PFF-style grade.

### Participation labeling rule (decision carry-forward A)
Participation is 2016–2025, historical only, with man/zone on ~49% of plays. **Anything
derived from it is a multi-season tendency, not current-season behavior.**
- Signal and column names end in `_hist`.
- `inputs_version` names the seasons used (e.g. `pbp_participation@<ts>[2023-2025]`),
  and the registry entry states the span.
- The UI shows the span next to the value ("38% man, 2023–25"). "This defense plays 38%
  man" must never read as "this year."

  - Multiply by 1.2 for page overhead and upsert churn, then add ~56 B of indexes.
  - A null costs 1 bit.
- **Season = 19 REG-week equivalents** (18 + postseason).

### Retention policies (decided; amended at step 5, 2026-09-27)
- **L2, staged player tables:** `ngs`, `ftn`, `pfr_advstats`, and `player_game_pbp`
  keep `season >= current_season - 1`.
  - Everything older is re-fetchable from nflverse, and backfills already refetch via
    `seasons_override`.
  - **`player_week` and `snaps` are exempt (amended 2026-09-27, user).** They were in
    the original L2 list.
    - Efficiency reads them for season and season−1, and so do both recompute paths
      that re-run it for past seasons (`scripts/backtest.py`'s r-sensitivity run and
      `scripts/backfill_efficiency.py`).
    - The backtest's parity check compares one stored week (2021 wk 10) and can't catch
      those inputs going missing (`docs/phases/P5.md`, open items 1–2).
    - Cost: ~13.5 MB/season kept (2025 measured sizes).
  - `team_week` is exempt (tiny; the backtest uses 2018+). So are `depth` (latest only)
    and `participation_player_season` (0.5 MB/season; it feeds the display-only `_hist`
    values, and their window needs the three seasons before the current one).
- **L4, player tables: deferred to step 7 (user, 2026-09-27). Not built at step 5.**
  - The proposal: once a season is complete, delete every
    `player_usage_week`/`player_eff_week` row for that season except each player's
    latest-week row.
  - **What it would destroy: point-in-time weekly player history, unrecoverably.** Each
    weekly row is what was known before that week, like the efficiency signals.
    Refetching the season and re-running the analysts gives nflverse's current revision,
    not the as-of values. It can't reproduce the rows L4 deletes.

      recomputable.
  - A backtest of any model input built from weekly player values would need exactly
    those rows.
  - Decide at step 7, with the measured size of both tables in hand.
- L2 runs in the L0 retention job (`pipeline/orchestration/retention.py`). It is a dry run
  by default, and deleting needs an explicit `--delete`.

  `position` column; join `snaps.position`.

**The load-bearing new engineering is the player-keyed pbp aggregation.**
- `player_week` has no success flag, and pbp's `run_location`/`run_gap` are never
  aggregated to a player grain.
- `player_game_pbp` (counts and sums, grouped by passer/rusher/receiver id, joined to
  FTN by `game_id`/`play_id`) supplies:
  - success rate
  - rush EPA/success by gap and direction
  - stuffed rate (`yards_gained <= 0`)
  - FTN-flag splits per player
- The team-defense-by-gap split is its team-level companion.

**Pressure rate / run-stop rate (unit-side):**
- Pressure rate: `def_pressures` over a pass-attempts-faced denominator.
- PFF-style per-defender run stops have **no free source**. PFR `def` is
  pass-defense-only. The honest substitute is team rush EPA/success by gap.

**Alignment (slot/perimeter) matchups are dropped from scope (decision, 2026-09-22).**
- No receiver-alignment or nearest-defender-role field exists in any free source.
- Where a directional split helps, use pbp's `pass_location`, labeled as a field-location
  split, never as slot/perimeter.

   - **Spec: the per-analyst input gate (design 2026-10-01, no code yet).** For Usage and
     Player efficiency. Both candidate keys are branches of item 2, and the logger's week
     picks one.
     1. **Where it lives: in each analyst's `inputs_ready`, before `compute()`.**
        - It compares the database against the analyst's own last successful run, not
          against this tick's collector results. So it recovers on its own:
          - a run that failed on the tick its inputs changed runs again next tick;
          - a manual `pipeline.run nflverse_bulk` between ticks is seen;
          - so is a retention delete.
          - A tick rule sees only this tick's writes, and misses all three.
        - Dispatcher and manual runs gate the same way (`pipeline.run usage` without
          `--force`).
        - The dispatcher can't see per-dataset changes anyway. `RunResult` carries no
          `meta`, so a dispatcher-level gate would mean widening `RunResult` and parsing
          the bulk collector's meta.
        - **The outer tick rule (decision 6: run only when `nflverse_bulk` wrote rows)
          keeps the hole the gate closes.** If the analyst fails on the tick bulk wrote,
          or bulk ran by hand, nothing invokes it again until bulk writes again.
          - A gate check costs ~0.25 s and ~300 bytes (item 2), so the outer rule saves
            no egress.
          - **Recommended: drop the outer rule for these two, and let the gate decide on
            every tick that runs analysts.** Keeping both (decision 2) is the user's call;
            if it's kept, item 5's auditor check covers its hole.
     2. **What "changed" means.** The gate builds a key and stores it in the run's
        `meta.gate`. It runs when the key differs from the last success's key. Both
        branches include:
        - `season` and `week`;
        - a code fingerprint: sha256 of the analyst module,
          `pipeline/core/player_tables.py`, and its migration (`0031`/`0032`, which sets
          `COLUMNS`). A deploy that changes a formula, k/r, or a column runs once;
        - a gate version constant, bumped whenever the gate changes.

        **Branch A, marker.** Each `_INPUTS_VERSION_KEYS` marker, plus `nflverse:players`.
        Cost: 7 one-row `source_freshness` reads, under 1 KB.
        - False runs on every marker move without content. Already seen: 1044 (PFR moved,
          0 rows changed), 1068 (`player_game_pbp` and `player_week` moved, 0 rows).
          `players` moves on any player field, not only `position_group`.
        - **False skips** when content changes without a marker move: a forced or
          `--seasons` bulk run, a retention delete, a manual fix.

        **Branch B, content.** Per input, `md5(string_agg(content_hash, '' ORDER BY
        <pk>))` over exactly the read's own WHERE. For `players`, the digest is over
        `player_id || ':' || position_group` only: its `content_hash` also covers names
        and status, which the analysts don't read.
        - Sound because `content_hash` is every stored non-key column plus `player_id`
          (`nflverse_bulk._finalize`, and the PFR and snaps paths). Nothing updates these
          tables outside that path.
        - Any insert, update or delete inside the window changes the digest. The logger's
          `rows_changed` can't see deletes; the digest can.
        - The digest's WHERE is built from the same constants `_fetch` uses, never a copy.
        - **Cost, measured 2026-10-01:** read-only, client wall time over 3 runs, week-4
          window (data through week 3).
          - All seven Player efficiency digests in one statement: **0.25 s, ~290 bytes**.
          - Its `_fetch` over the same window: 3.2 s and 10.8 MB.
          - Server-side the digest scans the rows the read scans (`snaps` by seq scan, with
            a 3 MB sort spill). Its time grows with the read; its egress doesn't.

        analyst and per bulk run. M = any of its inputs has `key_moved`; C = any has
        `rows_changed > 0`.
        - Marker (A) only if there are no M-without-C runs and no C-without-M runs (markers
