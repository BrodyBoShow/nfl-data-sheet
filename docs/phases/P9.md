## 0. Decisions (user, 2026-10-01)

### D1. Display-only. Not a model input.
It gets the same treatment as the players section: a **"not used by the model"** block
on the game page.
- **Why:** feeding a new input into L3 means re-fitting, re-validating and re-grading
  everything downstream, with `edge_validated` already false project-wide. Doing that
  mid-season for an unproven feature risks the part that works.
- **So:** ship it as display, let it run a season, and promote it to a model input only
  if it earns promotion. Promotion would be its own decision, with its own refit and
  backtest (§5).

### D2. Nothing counts as "started", so the concept is "projected primary", never "projected starter".
- **The data:** no stored column says who started. `depth` keeps no history, and `snaps`
  has no started field. Any definition would be a proxy.
- **So the definition is what the data supports.** A team's *primary* at a position
  group in a game is **the player with the most snaps at their `players.position_group`
  in that game.** A *projected primary* is the projection of that for an upcoming game.
  - Narrowed by D3 (defensive snaps for defensive groups) and D4 (OL and DB show no
    single player).
- **Why the name matters:**
  - For QB the proxy is near-exact. For a slot receiver or a rotational edge rusher it
    isn't close. "Starter" is a claim the data can't back.
  - This project's credibility rests on not making such claims: the garbage-time line,
    the dimming rules, "not used by the model", `edge_validated` false.
  - **The name is part of the honesty surface, not cosmetic.** Don't rename it back.
  - Made testable, not left to convention: "starter", "starting" and "starts" are banned
    words in this block's copy (§3, "Page").

### D3. DL, LB and DB use defensive snaps.
- D2's wording said "offensive snaps", which is ~0 for a defender. Defensive snaps are
  the obvious analogue, and the measurement below already uses them.

### D4. OL and DB show no single primary.
- **Why:** the measurement decided this against D2's own wording.
  - At 99.8% (OL) and 89.2% (DB) near-ties, naming one player is a claim the data
    refuses.
  - That's the false precision the rename exists to prevent.
- **Per group:**
  - **OL:** the five by snap count, unranked, labelled as a unit.
  - **DB:** the same, for however many the group carries.
  - **QB, RB, TE:** a single primary.
  - **WR, DL, LB:** a single primary, with the group's near-tie rate shown on the page.
- **D2 and D4 don't contradict each other:** D4 narrows D2's "the player with the most
  snaps" for OL and DB, where the data can't support one player.

### D5. The projection rule is last game's primary.
- **Why:**
  - It's the measured baseline.
  - It's point-in-time safe: it reads only games before the one being projected.
  - Its per-group hit rate is already known (table below).
  - A most-`_l4`-share rule may beat it, but shipping an unmeasured rule because it
    sounds better is the mistake this project has consistently avoided.
- **To test the alternative:** `scripts/compare_primary_rules.py` compares last game's
  primary with the most `_l4` snap share.
  - It covers the six single-primary groups, over 2025 and 2026 to date.
  - It reports each rule's hit rate with a Wilson 95% CI, and the paired per-game
    difference with a bootstrap 95% CI. Both come from `pipeline/core/stats.py`.
  - It reads through the Usage analyst's own `_fetch`/`build_usage_rows`.
  - Its rule logic is tested on fixtures (`tests/test_compare_primary_rules.py`).
- **It runs after the calibration window,** never during it (`P6.md`, Open 1).
- **Switch only if `_l4` wins by a margin that survives the CI:** the difference's CI
  lower bound must be above 0. Until then the shipped rule is last game's primary.

### D6. It's a view over `player_usage_week` (option A), not a new analyst (B).
- **Why:**
  - **Cheaper:** no new job, no scheduled read, no CLAUDE.md L2 amendment, no input gate.
  - **Safer.** This inverts what this spec said earlier. It argued (B)'s own player table
    was the structurally safer home, because synthesis is barred from player tables.
    That argument actually favours (A).
    - Under (A) the data never enters `signals` at all. It's derived from a player table
      that synthesis is already barred from by grants, and exposed only through a `web`
      view.
    - So display-only is enforced by grants, not by convention.
  - (B)'s only remaining advantage was supporting a depth-based rule, which D5 rules
    out.

### D7. The input gate (Q4.1) doesn't apply under (A).
- There's no scheduled job to gate. It's kept here, not deleted, in case (B) ever comes
  back.

### D8. The horizon, and week 1. Both inferences are confirmed.
- **Horizon:** the game page's own game, as of week − 1.
- **Week 1:** one line and no query, the same as the players section.

## 1. What it's for

A display block on the game page, "not used by the model" (D1). It shows who played the
most snaps at each position group in the team's last game, which is D5's projection for
this game, and how settled that is. It answers no model or betting question.

## 2. Inputs

**`player_usage_week` only** (D6), through the existing `web.player_usage` view's
underlying table.
- **Its columns carry what's needed:** `position_group`, the `off_`/`def_snap_share_game`
  shares, `team`, `week`, `game_id`.
- Within a team-game, the share ranks the same as the snap count (one denominator).
- **PFR-derived** (from `snaps`): SRL credit and a provider tag in the column head, as in
  the players section.
- **Never `depth`:** D5 rules out a depth-based rule, so the no-history problem doesn't
  arise.
- **No `snaps`-to-`games` join:** the Oakland trap in `P7.md` open item 7 doesn't apply.

**Drop risk: a missing row becoming a confident answer (filed 2026-10-01, user).**
- **The risk.** `player_usage_week` holds only players present in `players` (the Usage
  analyst drops the rest: `skipped_not_in_players` in its run meta).
  - If a game's most-snaps player is one of those, the view doesn't pick a *different*
    primary. It picks the **wrong** one.
  - The page then states it as fact, with nothing to show an input was incomplete.
  - It's the same shape as the defense-gate finding (`P7.md`, Player efficiency): a
    missing row silently turning into a confident answer.
- **Measure it after the calibration window,** against the database. It's in the
  post-window queue, after D5's comparison. Over 2025 REG, per position group, as a rate
  per team-game-group, like the near-tie table:
  1. How often does the primary from `player_usage_week` differ from the primary from
     `snaps`?
  2. Of those, how many differ because the `snaps` primary is absent from
     `player_usage_week` entirely, and how many for some other reason?
  - The `player_usage_week` side comes through the Usage analyst's own
    `_fetch`/`build_usage_rows`, not hand-written SQL (CLAUDE.md).
- **What the result decides, before the view is written:**
  - **Zero across 2025:** the done-when parity check is enough, and nothing changes.
  - **Nonzero:** the view must detect an incomplete group and say so rather than name a
    player. That becomes a design requirement of the view, not a later fix.
- **Result:** pending. Recorded here when measured.

## 3. Where it sits and what it writes

**Outside the model's layer contract (D1, D6).** It writes no table and no `signals` row.
- **A new `web` view** over `player_usage_week` computes, per (team, game, position
  group), the last game's primary (or the OL/DB unit), as of week − 1.
- **Getting there takes a new migration and a `P6.md` §2 update.** CLAUDE.md: widening
  what anon reads is never a view tweak.
  - The migration grants exactly the view's columns.
  - `scripts/verify_anon_access.py` gets the view's allow-list, the same pattern as the
    players views.
- **Storage:** none. **Egress:** page regenerations only, measured once built.
- **Synthesis is barred by grants:** it never reads `player_usage_week` (CLAUDE.md), and
  nothing here touches `signals`.
- **The view and D5's script must agree.** Once the view exists, its picks for 2026 are
  checked against `project_last_game` (CLAUDE.md: verification calls the production
  logic, and here the view is production).

**Page (wording decided by the user, 2026-10-01; adjusted only for fit):**
- **Heading:** "Projected primaries · not used by the model"
- **Sub-line:** "Who played the most snaps at each position last game. Not a depth
  chart, and not who takes the field first."

- **Honesty suite:** "starter", "starting" and "starts" are added to this block's banned

- **Licensing:** whatever covers the players section covers this. If a narrator (P8)
