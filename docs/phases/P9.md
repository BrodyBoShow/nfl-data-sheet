## 0. Decisions (user, 2026-10-01)

### D1. Display-only. Not a model input.
It gets the same treatment as the players section: a **"not used by the model"** block
on the game page.
- **Why:** feeding a new input into L3 means re-fitting, re-validating and re-grading
  everything downstream, with `edge_validated` already false project-wide. Doing that
  mid-season for an unproven feature risks the part that works.
- **So:** ship it as display, let it run a season, and promote it to a model input only
  if it earns promotion. Promotion would be its own decision, with its own refit and
  backtest (§5).

### D2. Nothing counts as "started", so the concept is "projected primary", never "projected starter".
- **The data:** no stored column says who started. `depth` keeps no history, and `snaps`
  has no started field. Any definition would be a proxy.
- **So the definition is what the data supports.** A team's *primary* at a position
  group in a game is **the player with the most offensive snaps at their
  `players.position_group` in that game.** A *projected primary* is the projection of
  that for an upcoming game.
- **Why the name matters:**
  - For QB the proxy is near-exact. For a slot receiver or a rotational edge rusher it
    isn't close. "Starter" is a claim the data can't back.
  - This project's credibility rests on not making such claims: the garbage-time line,
    the dimming rules, "not used by the model", `edge_validated` false.
  - **The name is part of the honesty surface, not cosmetic.** Don't rename it back.

### How well the proxy holds, by group (measured 2026-10-01)
2025 REG, from `snaps` joined to `players.position_group`, 544 team-games per group.
- **Top two within 5%:** how often the runner-up's snaps are within 5% of the primary's.
  A high share means "the primary" is close to arbitrary.
- **Same as the previous game:** how often a team's primary is the same player as in its
  previous game. That's also the hit rate of the naive "last game's primary" projection.

| Group | Snaps used | Top two within 5% | Same as the previous game |
|---|---|---|---|
| QB | offense | 0.4% | 87.9% |
| RB | offense | 2.4% | 77.7% |
| TE | offense | 5.5% | 74.8% |
| WR | offense | 29.0% | 61.3% |
| **OL** | offense | **99.8%** | 58.0% |
| LB | defense (see Q2.2) | 28.1% | 76.2% |
| DL | defense (see Q2.2) | 27.0% | 56.8% |
| **DB** | defense (see Q2.2) | **89.2%** | 43.8% |

- **Weakest: OL and DB.** Five linemen, and most of a secondary, play nearly every snap,
  so a single "primary" there is close to arbitrary.
- **WR, DL and LB are moderate:** about 3 in 10 games have a near-tie.
- **QB is near-exact,** as D2 says.
- **The page must say this per group,** not only here (§3, "Page"). See Q1.3 for whether
  OL and DB are shown at all.

- **Q2.3 Depth-chart history: blocks only a depth-based rule.**

## 3. Where it sits and what it writes

**Outside the model's layer contract (D1).** L3 synthesis never reads it, and no card
field carries it. It sits where the players section sits: an L2 product read only by
`/web`, through the `web` schema's views as anon.

**Where it's computed: UNRESOLVED (Q3.1). Blocks building.** Two options fit the
recorded rules.
- **(A) A view over `player_usage_week`.** No new job, table or scheduled read.
  - The game's actual primary follows from `off_snap_share_game` ranked within (team,
    game, position group), since share and snap count rank the same within a team-game.
    A last-game or `_l4` rule is a window over the same rows.
  - Costs: a new migration and a `P6.md` §2 update (CLAUDE.md: widening what anon reads
    is never a view tweak).
  - It puts a rule into SQL rather than an analyst, which may count as L3 computing a
    metric. That's a layer question for the user.
  - It can't do a depth-based rule.
- **(B) A new L2 analyst writing its own small player-level table.**
  - The CLAUDE.md L2 rule must be amended first: only Usage and Player efficiency may
    write player tables.
  - A player table is the structurally safer home for D1. Synthesis is barred from
    player tables, while it *does* read `signals`, so a `signals` home would leave
    display-only enforced by convention rather than by grants.
  - Needs: a sector name, a docstring, and an architecture.md entry.
  - Its own read path needs costing in meter units once the calibration window ratio
    exists (`P6.md` Open 1). Whether the per-analyst input gate is mandatory for it is
    Q4.1.
- **Storage either way is small.** A row per (team, game, position group) is 32 × 8 × 18
  ≈ 4.6k rows a season. At P7's measured 453 B per `signals`-shaped row, that's
  ~2 MB/season. (B)'s own table would be costed on its own row shape before building.

**Page (same rules as the players section):**
- **Heading:** "not used by the model". No dimming, and ordered by role, never by
  confidence.
- **The `snaps` column head** carries the PFR provider tag. The SRL credit uses the
  section's single snap statement, and `/sources` already has the PFR entry.
- **The weak-group statement is shown on the page, per group,** from the table in §0,
  e.g. that OL and DB primaries are near-ties most weeks. The exact wording is
  UNRESOLVED (Q3.3, blocks the page). It's recomputed from data each season, not
  hard-coded.
- **Vocabulary:** "starter"/"starting" are banned in this block's copy and enforced by
  the honesty suite's vocabulary test. That's D2's rename made testable.
- **Licensing:** whatever covers the players section covers this. The P8 narrator clause
  applies if a narrator ever reads this block, since it's PFR-derived.

## 5. Grading

**What D1 and D2 settle:**
- **No backtest and no scheduled grader are required to ship it.** Display-only means
  nothing is fitted and no edge is claimed.
- **It's measurable without a lock,** if Q1.2 picks a snaps or usage rule.
  - The truth is the same proxy (most snaps in the game), and it lands in `snaps` after
    the game.
  - A rule that reads only weeks before the game recomputes point-in-time from stored
    rows, as the player tables' as-of rows do. So its hit rate is measurable afterwards
    by an offline `scripts/` job, the same way the model's backtest reads history.
  - A depth-based rule would need each projection stored before kickoff (Q2.3).
- **The bar to clear is known:** last game's primary, measured in §0.

**Still open:**
- **Q5.2 Promotion criterion: blocks promotion only, not shipping.**
  - Which metric (hit rate per group; something calibrated if the block ever shows
    probabilities)?
  - What margin over the "last game's primary" baseline?
  - Over what n?
  - Pre-registered before the season's data is examined (P5 practice).
- **Closed by D1:**
  - Q5.3 (lock), unless Q1.2 picks depth;
  - Q5.4 (a scheduled grader);
  - Q5.5 (the baseline is measured);
  - Q5.6 (backtest).
